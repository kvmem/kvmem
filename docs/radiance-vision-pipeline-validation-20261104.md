# Radiance 图片编码管线短任务验收（2026-11-04）

本轮完成 CPU 线程配置、图片分阶段统计、进程内 embedding LRU 和后台 CPU 视觉编码。测试只使用短请求。

## 实现边界

- 统一启动器和界面新增 `CpuThreads`（默认 2，范围 1–256）与 `VisionCacheMiB`（默认 256，0 关闭）。对应 `OMP_NUM_THREADS` 与 `KVMEM_RAD_VISION_CACHE_MIB`。后者在加载模型前验证。
- embedding 缓存属于一个 Engine，不跨模型或进程；同时核对 128 位内容 key、几何和完整 BF16 patch 数据。缓存载荷预算包括 identity patch 与输出 embedding；活动请求、编码上下文和分配器元数据另计。该缓存独立于 KVMem KV/状态缓存及 Host/SSD 配额。
- CPU worker 使用独立 Program、Ctx、激活 arena 和 stream；只借用只读视觉权重及 kernel 描述，语言模型的执行上下文不在 worker 上运行。每次只编码一张图，CPU 编码可与其他请求的 GPU decode 重叠。
- 编码结束后由调度线程发布 embedding。取消在算子间检查；后台操作持有自己的输入与输出。退出时先取消并 join，再释放权重和插件。编码错误只拒绝对应请求。
- API `timings.image` 与监控请求 `image` 保留独立的 decode、preprocess、queue、encode 耗时和缓存命中计数。CPU encode wall time 包括执行期间的权重触页；GPU 批次按 patch 数分摊。阶段可以重叠，不能相加当作请求耗时。多候选 API 汇总按实际 Item 去重。

## 环境与初轮证据

Linux、Intel Core i7-8700、RX 9060 XT gfx1200，GPU UUID `04007590-0000-1000-803f-e07311696099`。每组启动前检查 GPU 无其他计算进程。Qwen3.8-27B MXFP4 模型与前次 CPU 图片验收相同，embedding 在 RAM，FP8 KV/F32 state、MTP3、并发 2、context8192、B2048/R512、batch256、sink/recent128/512、Host3072MiB；本轮配置 CPU8线程、图片缓存64MiB。正常回复上限8–64 tokens，关闭思考，temperature0。

首轮 34 项检查通过。重复两张不同的 64-token 图片各自命中 embedding 缓存，encode_ms=0；同尺寸换图没有误命中，空间颜色正确。256-token 图片请求约9.431秒，其中 encode_ms约8118；同时的独立文本请求约0.982秒完成，此时图片仍在处理。各请求场景不同，这些测点不作为吞吐加速比。

最终监控版本复测保留了一条格式断言失败：取消后的回答正确描述左红右蓝，但使用自然语言，32-token 限额截断后续内容，未满足 LEFT=/RIGHT= 格式断言。该失败的终端摘要保留，原始归档随旧实例丢失；恢复验收另用原标准问法和64-token上限，并要求一张未缓存的新图片重新编码。

三张已完成图片（红蓝128、反转128、红蓝512）的 patch 数据与 BF16 embedding 均与异步化前保存的结果逐字节一致。这只证明这些样本的数值回归，不推广为自然图/OCR质量等价。

最终取消恢复组 25 项检查全部通过：确认后台编码已开始后断开客户端，约0.051秒退休该请求；随后原图片命中 embedding 缓存、另一张未缓存图片完成重新编码、普通文本回答正确。最终 parking、finishing、pending I/O、active archive 和 checkpoint 计数归零。服务退出后 GPU 无计算进程，整卡已用显存回到59895808 bytes。

最终取消组整卡显存采样峰值15279898624 bytes，RSS采样峰值5044133888 bytes，VmHWM5194436608 bytes，Swap为0。每0.2秒采样，包含加载，可能遗漏更短峰值；与其他版本的不同请求集合不作为受控内存对照。

机器可读配置、关键测点与验证范围见[记录](benchmarks/radiance-vision-pipeline-20261104.json)。原始请求、响应、监控、构建依赖记录和BF16样本保存在远端任务归档 `vision-pipeline-evidence-20261104.tar.gz`，5570879 bytes、187成员，SHA256 `d9a8cabaa53614cee09519d224080ed4573f2ed0ef7bb247aacd23614557251a`。旧实例生成归档时写入了逐成员大小/SHA256清单，但未取回本机。用户随后确认开发实例已更换，原归档不可从新实例恢复；上述归档 hash 是旧实例终端输出，未经过本地独立复核。本地保留源码、构建计划及终端结果摘要。

## 构建与自动检查

首轮 Ninja 默认计划为60个主机对象、1个HIP对象和4次归档/链接。审查后移除对公共 Config 的布局扩展，改用进程环境配置，保持 Config 和 Ctx ABI。对实际源码、完整依赖、编译命令和固定 SDK 进行核对后，以原命令定向编译21个主机对象、4次归档/链接。第二轮实时状态和计时去重为16个主机对象、4次归档/链接；最终预算参数单测为1个主机对象、1次链接。

所有阶段均无 GPU 内核编译，现有 kernel 库哈希不变，最多8并行。未修改 Ninja 成功记录或用时间戳隐藏源码变化。新对象缺少可用 Ninja 依赖记录时，使用相同编译选项的预处理依赖输出来补全检查。此二进制为有记录的定向验证构建，未发布安装包。

原生缓存测试覆盖关闭、预算越界/无效值、容量不足、LRU淘汰、重复插入、不同几何、故意相同128位key但不同patch、调用者修改输出后的缓存隔离。17个原生补丁完整反向重建及正向应用通过，688个文件与开发树比较一致。Python后端测试83项、启动器12项、控制台HTTP桥接14项通过；启动器浏览器回归通过；监控浏览器回归验证了中英文图片阶段耗时和命中数显示。

## 提交前审计修复

审计补丁单独追加到此前已实测的管线补丁之后，保持历史源码和二进制身份可区分。可选 embedding 缓存的 get/put 改为分配失败时回退；替换条目先完成分配，再更新 LRU 和预算，逐个分配位置注入失败验证旧条目和计账不变。CPU 排队、上下文创建和线程启动失败只标记对应请求失败。异步入口限定在 KVMem observer 路径，原生独立服务的同步多媒体处理得以保留。

审计版本检查18个有序原生补丁的完整结果，与开发树688个文件比较一致。复用本机固定 WSL host 构建，dry-run 为10个主机对象和1次缓存测试链接；9个对象覆盖本轮引擎改动，未链接/构建整个引擎或GPU内核。GPU实测数据属于审计补丁之前的版本；此次审计未在新机器重建模型并重复GPU测试。

CI 对明确的 Radiance 改动单独运行原生源文件、便携契约、Python和界面检查。其他后端源码、未知公共路径或非 Radiance 工作流配方变化仍回退完整资格检查。

## 验证范围

实机范围为单卡 Linux CPU 编码、合成 PNG、FP8/F32、MTP3、两路请求。本轮未资格验证 GPU resident 图片缓存、Windows、TP2、JPEG、自然图/OCR、视频/音频及其他CPU ISA；未运行256K任务，未部署常驻服务。
